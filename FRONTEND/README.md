The Basic Idea T-REX is a centralized digital deactivation-request management platform. After a person's death, their digital identity, documents, subscriptions, financial services, insurance services, memberships and other online services may require separate closure or deactivation procedures. T-REX acts as a secure coordination layer that helps an authorized requester initiate, verify, organize and track these requests from one place. Core concept: One verified case → multiple relevant service requests → organized processing → centralized status tracking. Important: T-REX does not itself have authority to deactivate every external service. The respective service provider remains responsible for approving and executing the final deactivation.
How the System Works Step 1 — Authorized User Registration The requester creates an account and provides the information necessary to establish identity, relationship or authority, and information about the deceased. The system should not rely solely on user-submitted claims. Step 2 — Supporting Document Submission The requester uploads relevant supporting documents. The platform can process documents using OCR and validation workflows. OCR extracts information; it should not be presented as equivalent to authoritative verification. Step 3 — Requester Authorization The system checks whether the requester is appropriately authorized to initiate the request. This can involve identity verification, relationship or authority evidence, document checks, and additional review when required. Step 4 — Service Selection The requester selects the relevant services. T-REX creates individual service requests under one master case, making the overall process easier to manage. Step 5 — Organization-Specific Processing Where an official API or supported digital integration exists, T-REX can communicate through that integration. Where direct integration is unavailable, the platform can prepare and facilitate the appropriate request through the organization's established official channel. Step 6 — Request Tracking Every service request receives a status such as verification pending, request submitted, completed, or action required. The dashboard provides a consolidated view of the case. Step 7 — Notifications The platform can provide status updates when verification changes, additional information is required, a request is received, or processing is completed.
Security Architecture Authentication Only authenticated users should be able to access their cases. Authorization The platform should enforce role- and case-based access so a user can access only information they are permitted to view. Encryption Sensitive information should be protected during transmission and storage using appropriate cryptographic controls. Access Control Different roles—such as requester, verification personnel, administrator and integration components—should have different permissions. Audit Logs Important actions should be recorded with timestamps and relevant metadata to create an auditable history. Data Minimization Only information necessary for a particular request should be shared with the relevant organization.
